# Hackathon rules (adapted from juanlizarazo/hackathon-starter-kit, MIT)

These win over any stricter rule elsewhere.

## Scope
- HACK-01 Read the rubric before the brief. The rubric weights decide where hours go.
- HACK-02 The brief is the spec. Take its constraints literally.
- HACK-03 If a feature does not move a rubric criterion or the demo, skip it.
- HACK-04 Build the demo path end to end first, then widen.
- HACK-05 Simplest thing that demos well. No premature abstractions.
- HACK-06 Hardcode or seed data when real integrations would eat the clock. Make the seam obvious and label it.
- HACK-07 When a scoping call is ambiguous, ask. Do not silently build the bigger version.

## Testing
- HACK-08 No tests for coverage.
- HACK-09 Keep tests that exist.
- HACK-10 Small focused tests for the claims that decide validity: no violated capacity or state of charge limits, consistent units, correct baseline, reproducible results, savings not caused by doing less work.
- HACK-11 Verify by running the app and walking the demo path. Report what you clicked and saw.

## Demo polish
- HACK-12 Loading, empty and human friendly error state on every demo screen.
- HACK-13 Mobile must not look broken. Judges open links on phones.
- HACK-14 Seed realistic data. No lorem ipsum on the demo path.
- HACK-15 Keep README current: pitch, live link, demo flow, demo shortcuts.

## Last mile
- HACK-16 Audit the build against the brief in a fresh session, scoring each requirement as a percentage.
- HACK-17 Persona reviews: staff architect, UX lead, the sponsor (Torus).
- HACK-18 Reserve 2 to 3 hours for UI polish after the demo path works.
- HACK-19 Ship a live URL judges can touch. Submission is repo plus deck.
